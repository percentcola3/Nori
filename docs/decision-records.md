# ForgeSweep 决策记录

记录与最初《macOS 清理工具 Swift 重写方案》的有意偏差及其安全论证。每条记录一个决定：为什么偏离、以什么条件成立。

## DR-1 · App-only 形态（2026-09-27 确认）

**决定**：不实现方案 §0 的命令行（含 TUI）前端与 Homebrew 分发，只维护 SwiftUI App。
**理由**：产品已有自己的客户端载体，功能层（Services/策略/安全）与前端解耦，未来补 CLI 时可直接复用；不为不存在的消费者维护参数面（`--dry-run/--yes/--json` 等）。
**约束**：任何新增能力必须先落在功能层（可测试的 Services），不得写死在视图里，保证未来第二前端的可行性。

## DR-2 · 菜单栏常驻与定时能力（追认）

**决定**：追认超出方案 §1.2「不做常驻后台监控、定时清理、通知或菜单栏常驻」的部分：菜单栏常驻、每小时自动清理调度、流量监控、剪贴板历史。
**安全前提**（缺一即应回退本决定）：
- 自动清理只走 `automatic` 执行模式：执行前重新读取完整运行态快照，快照不完整直接放弃本轮（fail-closed）。
- 自动规则不得与模型、用户会话、Docker 数据或系统根目录重叠（`isForbiddenAutomationPath`）。
- 自动清理沿用与手动清理完全相同的删除漏斗（身份核对、白名单、打开文件检查）。

## DR-3 · 部分扫描结果保留展示（替代方案 §2.5）

**决定**：扫描超时/不完整时不整批丢弃结果，保留已确认完成的部分。
**安全等价论证**：方案要求整批作废的目的是防止半截结果流入删除。当前实现满足同一不变量：未完成目录单独列入 `deferredPaths` 展示；`cleanupScanComplete == false` 时所有条目强制取消勾选（不可执行）；不完整快照不写入完整结果缓存（5 分钟缓存复用不会继承）；执行前仍有逐项身份复核。UX 更好（用户能看到扫描到了哪里），安全性不降。

## DR-4 · 处置矩阵按方案 §5.3 对齐（2026-09-27 修正）

**决定**：修正两处与方案相反的处置：
- **安装包（installer）→ 移入废纸篓**（原实现为永久删除）。安装包可能是用户唯一的副本。
- **项目产物（purge）→ 永久删除**（原实现经 bridge 移入废纸篓）。构建产物可本地重建，进废纸篓只会让用户再清一次。

落地方式：`AppState.permanentFamilies = [.clean, .purge]` 是处置的唯一事实来源，确认文案（`confirm.cleanupPermanent.*` vs `confirm.apply.trash.*`）、bridge 环境变量（`SIMPLEMOLE_DELETE_MODE`）与执行汇总（`cleanup.execution.summary.permanent`）全部从它派生。移入废纸篓失败时绝不降级为永久删除。

## DR-5 · 删除出口集中与静态审计（2026-09-27 新增）

**决定**：永久删除不再使用路径字符串 API，改为 fd 链删除：从 `/` 逐级 `openat(O_NOFOLLOW|O_DIRECTORY)` 打开，最终句柄上核对 `(device, inode)` 后在已打开描述符下递归 `unlinkat`，全程不重新解析路径。`script/audit_destructive_sinks.sh` 纳入 `test.sh`：Swift 侧底层删除调用只允许出现在白名单文件（NativeCore 为用户数据唯一漏斗，其余仅清理应用自建临时文件）；bridge 侧 `mole_delete` 必须显式携带身份参数，`rm -rf` 只允许作用于脚本自建目录变量。
